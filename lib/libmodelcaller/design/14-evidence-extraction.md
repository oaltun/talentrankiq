## 14.1 purpose

two narrow llm steps bolt onto the evidence pipeline without touching
the embedding path: (1) **schema discovery** — a job ad becomes a typed
`ExtractionSchema` field list, once per ad; (2) **constrained
extraction** — a cv becomes `CvEvidence` with the ad-specific
`extensions` block filled against that schema, once per cv. the model
never judges depth; it only fills fields. rules (fixed weights) and the
judge (learned) score the result.

## 14.2 external commands (modelcaller stdio JSONL)

### discover_schema

request:

```json
{"id":"d1","type":"request","payload":{"cmd":"discover_schema",
 "ad_text":"...","model":"qwen2.5-1.5b-instruct-onnx-q4",
 "opts":{"max_new_tokens":256}}}
```

response payload:

```json
{"cmd":"discover_schema","schema":{"base":"v1","fields":[...]},
 "raw":"...model text...","gen_ms":8123}
```

- prompt: few-shot template (2–3 hand-written ad → schema pairs) + the
  ad, rendered with the qwen chat template. the model emits a json
  field list; modelcaller repairs (strip fences, truncate to balanced
  braces), parses, and validates every field through
  `libcvevidence::SchemaField` (name/type/description/required/enum).
  unparsable output → `ModelError::invalid_output` (caller falls back
  to hand-curated family schema or base-only evidence, §18.4).
- fields are clamped to sane limits: max 12 fields, names snake_case
  `[a-z_]{3,40}`, unknown `type` strings drop the field.

### extract_constrained

request:

```json
{"id":"e1","type":"request","payload":{"cmd":"extract_constrained",
 "cv_text":"...","schema":{"base":"v1","fields":[...]},
 "model":"qwen2.5-1.5b-instruct-onnx-q4",
 "opts":{"max_new_tokens":400}}}
```

response payload:

```json
{"cmd":"extract_constrained","extensions":{"years_professional_java":6},
 "dropped":["seniority_band"],"issues":[],"gen_ms":15200}
```

- the discovered schema travels in the request; the wrapper's
  constrained decode makes structurally invalid json impossible
  (04-generation.md §4.4). modelcaller validates the returned object
  through `ExtractionSchema::validate_extensions` (per-field drop,
  §18.2 rules) before responding.
- **base fields are NOT generated by the model.** the caller (bench /
  judgetrainer / gui) merges: stage-a deterministic `CvEvidence` for
  the base + these `extensions` + `extensions_schema` =
  `schema.hash()`. keeping base deterministic preserves the m1 contract
  (evidence cache keys stay stable) and bounds llm cost to the
  ad-specific part.

## 14.3 prompts

rendered in modelcaller (model-specific, like the usage adapters):
qwen2 chat template with a system line ("you fill json forms; output
only json") + the few-shot/user content. templates are `const`s in
`commands.rs` next to their commands — no config surface in v1.

## 14.4 session lifecycle

`load` the extractor (or discoverer) model on first use of either
command, keep it loaded until `shutdown` (same lazy-load rule as
embedders). `discover_schema` and `extract_constrained` may use two
different models (a stronger discoverer is once-per-ad cheap, §18.4);
each model gets its own session, spawned through the existing
`--wrapper` path.

## 14.5 registry / config

- triq.yaml gains one family + one model:

```yaml
families:
  - family: qwen-instruct
    usage: extraction-json
models:
  - slug: qwen2.5-1.5b-instruct-onnx-q4
    family: qwen-instruct
    kind: extractor
    dim: 0
    max_context_window: 4096
    source: hf:onnx-community/Qwen2.5-1.5B-Instruct
    onnx_url: https://huggingface.co/onnx-community/Qwen2.5-1.5B-Instruct/resolve/main/onnx/model_q4.onnx
```

- `usage: extraction-json` means "no query/doc prefix adapters; the
  caller supplies the full prompt" — `format_query`/`format_document`
  pass through untouched for this family.
- `kind: extractor` models are skipped by embed/rerank model selection
  (wrong-kind errors if requested there, same as today's cross-kind
  guards).
- the default discoverer is the same slug (§18.4: same runtime,
  different prompt); a distinct `schema_discoverer` slug can replace it
  without config shape changes.

## 14.6 caches (caller-side, same layout as the embedding caches)

- schema cache: `<cache_dir>/../schemas/<sha16>.json`, key =
  sha256(model \0 ad_text). value = the validated `ExtractionSchema`
  json. inspectable artifact, reviewed once, reused forever.
- stage-b evidence cache: `<cache_dir>/../evidence/<sha16>.json`, key =
  sha256("stage-b" \0 model \0 schema_hash \0 cv_text) — same
  `<cache>/../evidence` dir as stage-a, distinguished by the `stage`
  key part (bench's `EvidenceCache` already stages its keys; the
  on-disk value shape is `CvEvidence` either way). when the caller
  truncates the cv prompt (bench `max_chars`, 18 §18.6 m3a note), the
  stage part becomes `stage-b<n>` so a cache entry always names the
  prompt length that produced it.

## 14.7 review gate (m3a)

`review_schema: true` (bench/judgetrainer config): before any
extraction batch, every discovered schema is written to the schema
cache and the run **stops** with the schema paths listed; a human
inspects/edits them and re-runs — the second run finds the schemas
cached and proceeds. `false` (m3b, default off) discovers and
continues in one pass. gate failure mode is "stop", never "guess".

## 14.8 milestones

- m3a (this doc + 04-generation.md): both commands, wrapper generation,
  registration, caches, review gate. acceptance (18 §18.8):
  llm-evidence rules > deterministic rules on cnam-test; extension
  fields fill on fixture ads; review gate round-trips.
- m3b: flip the gate default; acceptance: auto-discovered schemas match
  reviewed ones on fixture ads (field-level agreement), no nDCG
  regression vs m3a.
